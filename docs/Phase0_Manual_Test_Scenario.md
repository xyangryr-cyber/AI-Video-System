# Phase 0 需求定义 — 手动测试场景（浏览器逐步执行版）

> **目标**: 供测试人员从零开始在浏览器中逐步验证 Phase 0 的全部核心功能
> **前置条件**: 系统 `docker compose up` 已启动，`http://localhost:3000` 可访问
> **测试方式**: 每步包含操作和预期结果，框内为检查点。按顺序执行，任一步不通过即标记 FAIL 严谨直接调用API 完成所有测试后产出测试报告 给出每一个测试场景的测试方法

---

## 场景总览

本测试覆盖 5 个核心场景，按顺序执行：

| # | 场景 | 验证目标 |
|---|------|---------|
| 1 | 创建项目 + 生成完整需求定义 | 主题+描述 → 结构化 requirements.json |
| 2 | 自然对话修改需求 | revise 修改字段、regenerate 重做、Router 意图识别 |
| 3 | 澄清问题处理 | 信息不完整时的交互流程 |
| 4 | 偏好提取与确认 | PreferenceExtractor 从对话中学习偏好 |
| 5 | 门禁与推进 | GateKeeper 校验 + 进入 Phase 1 |

---

## 场景 1: 从主题和描述生成完整需求定义

### 目的
验证用户输入标题+自然语言描述后，系统能生成包含主题、观点、时长、平台、分类、字数的完整结构化需求。

---

### 步骤 1.1 — 进入创建项目页面

| 操作 | 打开浏览器，访问 `http://localhost:3000/`，点击右上角"+ 新建项目"按钮 |
|------|------|

```
[检查点 1.1a] 页面右上角存在"+ 新建项目"按钮，且为可点击状态（非灰色）
[检查点 1.1b] 点击后地址栏跳转到 /projects/new
[检查点 1.1c] 页面显示以下元素：
  - 一个标题输入框
  - 一个描述输入框（多行文本区）
  - 一个"提交"按钮
```

---

### 步骤 1.2 — 输入标题和完整描述

| 操作 | 在标题框输入"2026年黄金价格走势分析与投资展望" |
|------|------|

| 操作 | 在描述框输入以下内容（确保 ≥ 10 字）： |
|------|------|
| "本视频分析 2026 年黄金价格走势。核心观点是美联储降息周期下黄金仍有上行空间，建议投资者关注实际利率变化和央行购金动态。预期时长约 8-12 分钟，发布在 B 站。" |

| 操作 | 点击"提交"按钮 |
|------|------|

```
[检查点 1.2a] 页面跳转到 /projects/{project_id}（project_id 格式为 proj_YYYYMMDD_NNN）
[检查点 1.2b] 页面左侧阶段导航中 Phase 0 高亮显示（蓝色）
[检查点 1.2c] 页面中央对话区顶部显示第一条消息：用户刚提交的标题和描述
[检查点 1.2d] 对话区底部显示"正在分析你的需求..."加载指示器
[检查点 1.2e] 页面右侧任务清单面板显示两个任务：
  - generate_artifact → 状态为 🔄 running
  - review → 状态为 ⏳ pending
```

---

### 步骤 1.3 — 等待 RequirementsAgent 生成完成

| 操作 | 等待任务清单中 `generate_artifact` 状态变为 ✅ succeeded（预计 3-15 秒） |
|------|------|

```
[检查点 1.3a] 对话区追加一条 Agent 回复卡片，内容为结构化需求摘要，包含：
  - 标题: "2026年黄金价格走势分析与投资展望"
  - 主题: 涉及黄金价格走势、美联储降息、央行购金等
  - 时长范围: 8-12 分钟（从用户描述中提取）
  - 平台: B站
  - 分类: 金融财经 > 行业分析（或相近子类）

[检查点 1.3b] 需求摘要卡片上的平台规格显示为 B站参数:
  - resolution: "1920x1080"
  - bitrate: "8Mbps"
  - format: "H.264 MP4"

[检查点 1.3c] 卡片中显示目标字数范围约为 1536 ~ 2880 字
  （计算：8×240×0.8=1536, 12×240×1.2=2880）

[检查点 1.3d] 卡片中已确认的字段右上角有绿色勾标记

[检查点 1.3e] 任务清单中 generate_artifact → ✅ succeeded
[检查点 1.3f] 任务清单中 review → 🔄 running（自动触发）
```

---

### 步骤 1.4 — 等待 CompletenessReviewer 审核通过

| 操作 | 等待任务清单中 `review` 状态变为 ✅ succeeded |
|------|------|

```
[检查点 1.4a] 任务清单中 review → ✅ succeeded
[检查点 1.4b] 对话区底部出现"确认进入下一阶段 → Phase 1"按钮
[检查点 1.4c] 按钮为高亮可点击状态（因为我们提供了完整信息）
```

## 场景 2: 自然对话修改需求

### 目的
验证用户通过自然语言对话修改已生成的需求，Router 正确识别意图，RequirementsAgent 正确更新字段。

> 注意：场景 2 紧接场景 1，使用同一个项目继续操作。

---

### 步骤 2.1 — revise 修改特定字段（时长）

| 操作 | 在对话区底部输入框输入"把时长改成 15 分钟吧，我觉得 8-12 太短了" |
|------|------|

```
[检查点 2.1a] 用户消息出现在对话区
[检查点 2.1b] 任务清单中出现新的 user_revision 任务，状态为 🔄 running
[检查点 2.1c] Agent 活动流面板显示 Router 识别动作为 "revise"
```

| 操作 | 等待 user_revision 任务完成（状态变为 ✅ succeeded） |
|------|------|

```
[检查点 2.1d] 对话区需求增加一条消息：
  - target_duration_minutes 变为 {"min": 15, "max": 15} 或相近范围
  - target_word_count 重新计算：15×240×0.8=2880, 15×240×1.2=4320（约值）

[检查点 2.1e] 旧的 review 任务状态变为 ⤵ superseded
[检查点 2.1f] 任务清单中出现新的 review 任务（对应新版本产物）
```

---

### 步骤 2.2 — revise 修改发布平台

| 操作 | 在输入框输入"改成发视频号吧，不发 B 站了" |
|------|------|

| 操作 | 等待 user_revision 完成 |
|------|------|

```
[检查点 2.2a] 需求摘要卡片中 platform.primary 更新为视频号对应的平台标识（如 "wechat"）
[检查点 2.2b] platform.specs 按视频号规格更新：
  - resolution: "1080x1920"（竖屏）
  - bitrate: "4Mbps"
  - format: "H.264 MP4"
[检查点 2.2c] platform.secondary 中不包含 bilibili（用户明确说"不发 B 站"）
[检查点 2.2d] artifact_version 再次自增（如 v2 → v3）
```

---

### 步骤 2.3 — regenerate 重新生成

| 操作 | 在输入框输入"这版需求感觉不太对，重新分析一下吧" |
|------|------|

```
[检查点 2.3a] 任务清单中出现新的 generate_artifact 任务（而非 user_revision）
[检查点 2.3b] Agent 活动流显示 Router 识别动作为 "regenerate"
```

| 操作 | 等待新 generate_artifact 完成 |
|------|------|

```
[检查点 2.3c] 对话区出现全新的需求摘要卡片
[检查点 2.3d] artifact_version 再次自增
[检查点 2.3e] 所有旧 review 任务变为 ⤵ superseded，自动追加新 review
```

---

### 步骤 2.4 — Router 模糊意图 → clarify

| 操作 | 在输入框输入模糊表述"嗯……这个感觉不太对，你懂吧" |
|------|------|

```
[检查点 2.4a] 对话区出现 Agent 的澄清回复，内容大致为：
  "你是想修改需求的内容，还是想进入下一阶段？"
  或 "你是想修改目标时长，还是想更换发布平台？"

[检查点 2.4b] 任务清单不新增任何任务（clarify 不改动任务账本）
[检查点 2.4c] Agent 活动流显示 IntentRouter 输出为 "clarify"
```

## 场景 3: 澄清问题处理

### 目的
验证当用户初始描述缺少关键信息时，系统通过澄清问题引导用户补充，而非编造信息。

> 场景 3 需要创建新项目。

---

### 步骤 3.1 — 用不完整描述创建项目

| 操作 | 点击页面导航回到首页，再点击"+ 新建项目" |
|------|------|

| 操作 | 标题输入："聊聊地方债的问题" |
|------|------|

| 操作 | 描述输入（故意不提供具体观点、时长、平台）："最近地方债话题很热，想做个视频聊一聊" |
|------|------|

| 操作 | 点击"提交" |
|------|------|

| 操作 | 等待 RequirementsAgent 生成完成 |
|------|------|

```
[检查点 3.1a] 对话区需求摘要卡片中显示澄清问题区域（标记为"⚠ 需要你补充"）
[检查点 3.1b] 澄清问题至少覆盖以下维度：
  - 具体想从哪个角度分析（如：政策角度/经济影响/地方财政） → clarification_needed 含 "specific_angle"
  - 期望时长 → clarification_needed 含 "duration"
  - 目标平台 → clarification_needed 含 "platform"

[检查点 3.1c] 卡片中不应出现编造的细节（如"地方债规模已超 XX 万亿"）作为已确认内容
[检查点 3.1d] 卡片中已推断出的合法字段（如分类: 金融财经 > 政策解读）有绿色勾
[检查点 3.1e] 卡片中缺失字段显示橙色问号标记
```

---

### 步骤 3.2 — 通过对话补充缺失信息

| 操作 | 在输入框输入"从地方财政可持续性角度分析，8-10 分钟吧，发 B 站" |
|------|------|

| 操作 | 等待 RequirementsAgent 更新完成 |
|------|------|

```
[检查点 3.2a] 需求摘要卡片更新：
  - 主题变为具体观点（含"地方财政可持续性"）
  - target_duration_minutes 填为 {"min": 8, "max": 10}
  - platform.primary 填为 "bilibili"

[检查点 3.2b] 卡片中澄清问题区域缩小（待补充字段减少）
[检查点 3.2c] 之前缺失的字段从橙色问号变为绿色勾
```

---

### 步骤 3.3 — 补充后审核通过

| 操作 | 等待新 review 任务完成 |
|------|------|

```
[检查点 3.3a] 新 review 结果为 ✅ succeeded (PASS)
[检查点 3.3b] clarification_needed 数组变为空（或仅剩非关键维度）
[检查点 3.3c] "确认进入下一阶段"按钮变为可点击
```
